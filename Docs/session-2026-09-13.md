## The bug Oscar found on device
Backgrounding the game on the phone and reopening it **restarts the run**. Diagnosis: Android
kills backgrounded processes to reclaim memory; Unity then boots scene 0 (MainMenu) and the run is
gone. There was **no `OnApplicationPause` / `OnApplicationFocus` / `OnApplicationQuit` hook
anywhere in the project** — nothing was ever being saved. The OS behaviour cannot be prevented,
so the fix is snapshot + restore.

## Why it turned out easy
A run is almost entirely derived state. The one thing that looked hard — the board — isn't: a
landed piece carries no state beyond its type, because row, world position and sorting order are
all recomputed from its index in `Column._ingredients`. **A board is four `IngredientType[]`s.**
Replaying one through `Column.AddIngredient` rebuilds the stack exactly.

## What shipped

### New (`Assets/_Project/Scripts/Core/`)
- **`RunSnapshot`** — the DTO. Structure only, no inline defaults (`RunSnapshotService.Capture` is
  the single factory and fills every field). Public fields because JsonUtility requires them.
  `CURRENT_VERSION` guards the schema.
- **`RunSnapshotColumn`** — one column, bottom row first. Exists only because JsonUtility can't
  serialize a jagged array.
- **`RunSnapshotStore`** — PlayerPrefs persistence (key `runSnapshot`) + the in-memory `Pending`
  handoff across the scene load. Kept out of `SaveDataManager` on purpose: that owns the player
  PROFILE (constantly read, individually keyed, expensive to corrupt); this owns one throwaway
  blob whose worst-case loss is a single run. Every failure path returns null and drops it.
- **`RunSnapshotService`** — maps a live run to a snapshot and back.

### Saved / not saved
Saved: score, stars-this-run, `StarsPaidFromScore` (so a resumed run can't double-pay the
end-of-run payout), level + ingredients-placed, the per-run `IngredientRoster` order, the board,
chef position + facing, the Special Order (level/progress/recipe), the continue-used flag.

Deliberately **not** saved: falling pieces, the preview queue, the shuffle bag, an in-flight
consumable or fairy. A resume starts from a settled board with a fresh wave — a couple of
in-flight pieces vanish, which reads as a small gift, and the snapshot stays limited to what
genuinely can't be recomputed.

### The ordering problem (the one real design decision)
Unity's `Start()` order between same-priority scripts is **undefined**, so "GameManager restores
everything after EnsureManagers" is a race: `ChefController.Start` and `BurgerChallenge.Start`
both seed their own state and would overwrite a pushed value.

Resolved by splitting on **who already seeds the state**, not on timing:
- Self-seeding systems read `RunSnapshotStore.Pending` inside their existing seeding code —
  `DifficultyManager` (level), `IngredientSpawner.Awake` (roster), `ChefController` (position +
  facing), `BurgerChallenge` (the order). The snapshot is just another input to a decision they
  already make — the same shape as the existing `TutorialMode` gates.
- `RunSnapshotService.Apply` covers only what nothing else writes: run totals, the board, the
  continue flag.
- **`Pending` is cleared by whoever starts a scene**, never mid-scene: `SceneLoader.LoadGame()`
  clears it (a plain load means fresh), `SceneLoader.ResumeGame(snapshot)` sets it. That's what
  makes the handoff ordering-proof, and it made every existing `LoadGame()` call site correct for
  free (Restart, menu Play, the tutorial's closing reload).

### Write / clear points
- Written: `OnApplicationPause(true)` and `OnApplicationQuit` while Playing (`GameManager.
  SaveResumePoint`, which also refuses during the tutorial so a scripted board can't overwrite a
  real run), and by Quit to Menu.
- Cleared: `StartGame` (so Play, Restart and the tutorial's closing reload all discard it) and at
  game over. **There is only ever ONE saved run — whichever you were last in.**

### Product decisions (Oscar)
1. **Cold launch shows the menu**, with RESUME above PLAY — no auto-jump into the run. One code
   path, and a player who deliberately closed the app isn't dragged back into a losing board.
2. **Quit to Menu is now "pause and leave"**, not a forfeit — it saves the run, so the player can
   browse the shop or change a skin and come back to the same board. Nothing is paid out early;
   the end-of-run star payout still lands at the real game over. **Restart still forfeits.**
   (This supersedes the old "Quit forfeits the end-of-run score payout" rule in CLAUDE.md.)
3. **Art: `ui_btn_blue_wide`**, the only blue blank in the kit, at `MENU_RESUME_W` 330 (vs PLAY's
   400) above PLAY. PLAY never moves whether or not a run is waiting. If Lucia ever delivers a
   blue PLAY-shaped blank it's a one-line file swap.
