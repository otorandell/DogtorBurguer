## Headline

   speed curve, earlier/higher triple-wave chance, and faster overall pacing.
2. **New "Start Level" setting** (stepper in the Settings panel) — jump straight into any
   level. Built primarily as a playtest tool; persists like the other settings.
3. **Killer level (21)** — Tetris-style kill screen above the normal curve.
4. **Spawn composition reworked** — regular ingredients now come from a shuffle-bag (even
   spread, no droughts); buns decoupled into a self-balancing grid-aware economy.
5. **Two code-review passes** — found + fixed one real init-order bug (difficulty) and three
   minor cleanups; spawn rework reviewed clean.

## 1 — Start Level setting
- `SaveDataManager.StartingLevel` (persisted PlayerPref `startingLevel`, default 1, clamped

- `SettingsPanel` gained a `[−] Start Level: N [+]` stepper row (new layout constants in

- `DifficultyManager` seeds `_currentLevel` from `StartingLevel` (TestDualColumn still overrides).

## 2 — Difficulty redesign (table-driven)
Replaced the `Lerp`-based curve with three explicit per-level arrays in `GameplayConfig`
(indexed `level - 1`, each length `MAX_LEVEL`):
- `FALL_STEP_BY_LEVEL` — front-loaded: L1 **0.45**, L10 **0.205** (≈ old L15), L20 **0.10**.
- `INGREDIENT_COUNT_BY_LEVEL` — 7 types by L16 (was L18).
- `TRIPLE_CHANCE_BY_LEVEL` — starts **L6**, caps **0.50** (was: start L8, cap 0.35).
- `LEVEL_THRESHOLDS` reshaped — L20 at **394** placements (was 532): longer early levels,
  much shorter late ones, faster overall.
- Removed the now-dead `TRIPLE_WAVE_START_LEVEL` / `TRIPLE_WAVE_MAX_CHANCE` constants and the
  `ComputeTripleWaveChance` method; `ApplyDifficulty` now just indexes the tables.

**Playtest result**: dev reached L14 via normal progression — curve feels good; progression
maybe slightly fast but kept as-is (one-cell fix in `LEVEL_THRESHOLDS` if it ever grates).

## 3 — Killer level (21)
- `KILLER_LEVEL = 21`, above the curve and NOT in the tables. Applies `MIN_FALL_STEP_DURATION`
  (now **0.06**, repurposed as the absolute fall floor), 7 types, always-triple.
- `MIN_FALL_STEP_DURATION` had to drop 0.1→0.06 because `IngredientSpawner.SetFallSpeed` clamps
  to it — otherwise the kill-screen speed would be silently clamped back to L20's.
- Reached by sustained survival past `KILLER_LEVEL_THRESHOLD` (**434** placements). Selectable
  from Settings only while `SETTINGS_LEVEL_CAP == KILLER_LEVEL` (testing).

## 4 — Spawn composition rework (ingredient distribution + bun economy)
Triggered by spotting the `_forceBunMultiplier` scene-vs-config drift (live 2 vs documented 1.5),
which opened up a full rethink of `WaveComposer`. Old model = uniform independent rolls
(`Rng.Range(0, N+1)`: each type and "a bun" all `1/(N+1)`) + a forced-bun pacing counter.
Problems: streaks/droughts (memoryless), and bun frequency drifting with type count
(25% early → 12.5% late) because it was coupled to `1/(N+1)`.

New model — buns fully **decoupled** from regular ingredients:
- **`IngredientBag`** (NEW class): shuffle-bag for regulars — `1 of each active type +
  BAG_RANDOM_EXTRAS (3)` random extras, Fisher-Yates shuffled (via `Rng`), drawn without
  replacement, rebuilt from the current active count on empty / on count change. Kills
  droughts and streaks; the extras keep it non-countable. No weights (intended).
- **Bottom bun**: flat `BOTTOM_BUN_CHANCE` (0.12), level-independent. Drought guard forces a
  bottom after `BUN_DROUGHT_LIMIT` (15) bun-less pieces. Surplus bottoms cancel on the grid.
- **Top bun**: only when ≥1 open bottom exists (lone top self-destructs). Chance
  `min(TOP_BUN_BASE_CHANCE 0.08 + TOP_BUN_CHANCE_PER_EXTRA_BOTTOM 0.04·(open−1), CAP 0.40)`.
  = 8% at one open, +4% each more → crosses the 12% bottom rate at **2 open bottoms**, so the
  board self-balances around ~2 unclosed bottoms instead of accumulating.
- `WaveComposer` slimmed to orchestrate (bun-or-bag) + own the bag/drought counter;
  `GetBunType`/`GridHasBottomBun` deleted, `CountBottomBunsOnGrid` → `CountOpenBottoms`.
- `IngredientSpawner` dropped the two `Forced Bun Spawn` SerializeFields; `new WaveComposer()`.
  Removed config: `FORCED_BUN_MULTIPLIER`, `BUN_TOP_BASE_CHANCE/_PER_BOTTOM/_CAP`. Trimmed the
  orphaned `_enableForcedBunSpawn`/`_forceBunMultiplier` lines from `Game.unity`.
- **Playtested → "feels great."** Reviewed clean (no correctness findings).

## 5 — Code review (high effort) — findings + fixes
- **[Fixed, correctness] Init-order race on the starting level.** `DifficultyManager.Start`
  fired `OnLevelChanged` for any start level > 1, but all subscribers attach in their own
  `Start()` with no execution order set → (a) HUD could show "Level 1" until the next threshold,
  and (b) a spurious level-up SFX could play at game start. **Fix**: `[DefaultExecutionOrder(-100)]`
  on `DifficultyManager` so it seeds + applies difficulty before the HUD/spawner init, and dropped
  the init-time `OnLevelChanged` (initial level is now pull-state; subscribers read `CurrentLevel`).
- **[Fixed, cleanup] `MAX_LEVEL` was comment-only** after the refactor + **array-length invariant
  was unenforced** → one `Awake` `Debug.Assert` now checks all four tables are `MAX_LEVEL` long
  (re-wires `MAX_LEVEL` into real use and turns the "keep in sync" comment into a check).
- **[Fixed, cleanup] Comment drift** in `SettingsPanel` ("1..MAX_LEVEL" → "1..SETTINGS_LEVEL_CAP").

## Key decisions & non-obvious findings
- **Data model**: chose explicit tables over formula+exponent — surgical per-level feel control
  matches the playtest loop and removes the rounding-decided breakpoints of the old `Lerp`.
- **`SetFallSpeed` clamp** is why `MIN_FALL_STEP_DURATION` is now the kill-screen speed (single
  source: killer speed == absolute floor).
- **Pull vs push for initial level**: the level number is state, not an event. Every consumer
  already reads `CurrentLevel` on init (`GameHUD.RefreshAll`, `GameOverPanel`), so the init-time
  event was both unnecessary and a race/SFX hazard.
- **No Script Execution Order** existed for these managers — confirmed via grep; that's what made
  the `Start`-ordering race real. `DefaultExecutionOrder(-100)` is the fix.
- **Bun mechanic drove the bun design**: a burger completes only when a `BunTop` lands above a
  `BunBottom` in its column; a lone top self-destructs; two adjacent bottoms cancel. So bottoms =
  "start" resource (flow freely, self-cancel), tops = "close" resource (must be grid-gated or
  wasted). Decoupling let the existing top-vs-bottom mechanic stay untouched.
- **`_forceBunMultiplier` drift was the entry point** — live scene value 2 vs config 1.5; and that
  param actually made buns *rarer* (higher threshold = fewer forced), so it wasn't even the cause of
  "buns too common early" (that was the `1/(N+1)` = 25% random path). Whole thing deleted now.
